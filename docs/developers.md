# Developer guide

For working on the code: running it locally, previews, tests, releases and the security checks. Back to the [README](../README.md).

## Run
```sh
curl -LsSf https://astral.sh/uv/install.sh | sh     # once
uv sync
uv run club-minutes roster                          # rebuild data/roster.json from data/roster-sheet.json
uv run club-minutes import archive                  # optional: (re)build data/ from old minutes in archive/ (importer.py)
uv run club-minutes import-correction 2026-10-01 corrected.pdf --by N0CALL --reason "…" --on 2026-10-08  # imported minutes corrected later: original PDF = v1, this = v2, no notice
uv run club-minutes serve --host 0.0.0.0 --port 8765
uv run playwright install chromium firefox webkit   # once: the browser tests run in each (one not installed is skipped)
sudo .venv/bin/playwright install-deps              # once, on Linux: the libraries Firefox and WebKit need
uv run pytest -q                                    # the tests, the browser tests in all three, and ruff (pinned in uv.lock)
uvx ruff@latest check .                             # warn only: what the newest ruff would flag
```
People come from `data/roster-sheet.json` (the roster's two tabs, Member Roster and Membership Log, as grids of values). Copy it from a backup of the club's server, or start one with `uv run club-minutes first-member YOURCALL --first … --last … --email … --class General` (only when there's none).

PDF generation needs the system Pango library: `sudo apt install libpango-1.0-0 libpangoft2-1.0-0`.

## Previewing a branch
`deploy/preview.sh BRANCH` runs a branch on a development machine (ports from 8100) so it can be tried before merging, without touching the live server. It uses the local branch when there is one, so work can be previewed before it's pushed; otherwise the branch on GitHub. It prints the address and a one-time sign-in link (passkeys don't work on a bare IP address).
- **Preview mode:** a banner on every page; email is recorded on the **Email log** page (name menu → Email log, in admin mode) instead of being sent; roster edits go to a copy of the roster (`preview-sheet.json`), never the real one.
- Each preview has its own checkout and a fresh copy of `data/` (meetings, roster cache, bylaws) on every update; its sign-ins are kept.
- **Staging server** (server admin guide → Staging server): `deploy/stage-push.sh [BRANCH] [SSH-HOST]` installs a local branch there over ssh (default: the current branch on `minutes-stage`), without pushing it to GitHub; `update.sh` installs it with the usual rollback. Its data is the live app's, synced nightly.
- **The demo club:** `DEMO=1 deploy/preview.sh BRANCH demo` runs the preview with the demo club instead of the club's data: Example Radio Club (W0DEMO), twelve invented members (Jane Doe, N0JANE, is the president and admin, and the sign-in link is hers), three published minutes, business items, a chow schedule and calendar events, all dated around today. `demo/build.py OUTDIR` builds it through the app's own code (`demo/club.yaml` is its config), so it follows changes to the data files; `tests/test_demo.py` builds it and opens the main pages. Use it for screenshots and the video: every name, callsign (four-letter suffixes are never issued), email (example.org) and phone (555-01xx) is made up. `uv run python demo/screenshots.py` takes the README's screenshots from it (no server; the PREVIEW banner left out), and records in `docs/screenshots/manifest.json` which templates, CSS and scripts each one shows: `tests/test_guards.py` fails when one of those changes, naming the pictures to retake, but only for a release: with `CHECK_SCREENSHOTS=1`, which GitHub sets on pull requests to main and on main itself (run `CHECK_SCREENSHOTS=1 dev/checks.sh --full` at the freeze). Items on their way to `next` leave the screenshots alone, so they're retaken once per release instead of after every change to a page. Python changes aren't tracked: retake by eye when a page shows something new.
- `deploy/preview.sh --list` shows running previews; `deploy/preview.sh --stop BRANCH` stops one and deletes its copy.
- They run as user services (`systemctl --user`), so they stop if this user logs out entirely, unless lingering is enabled (`loginctl enable-linger`).

## Changes and releases
- Each PR that changes the app adds a line under "Unreleased" in `CHANGELOG.md` (Writing the changelog, below), and says which issue it settles, if any (`Closes #12`).
- **Stacked PRs** (one branch built on another, while earlier ones wait for review): each PR targets the branch below it, so its diff shows only its own change. To release the stack, a release PR from the top branch into main carries everything. Just before merging it, retarget every PR in the stack to main; GitHub then marks each one merged when the release lands, because its commits are in main. A PR left targeting another branch stays open and has to be closed by hand. Keep stacks short where possible.
- To release: in a PR, rename "Unreleased" to the new version and date and bump `version` in `pyproject.toml` (then `uv lock`). When it merges, the Release workflow tags the merge commit `vX.Y.Z` and publishes a GitHub release with that CHANGELOG section. Deploy with `update.sh`; the footer then shows the new version.
- **Releases that need steps by hand** (a config change, a data file to copy, a new secret): add a line `- **Deploy notes:**` to that version's CHANGELOG section, with the steps indented under it as a numbered list. Put each command or file content in its own code block (indented 8 spaces under its step), one step per action, so they can be followed and copied. The admin Updates page shows them, formatted, and asks the admin to confirm they're done before updating. Only steps the release needs belong here; optional server hardening goes in this README.
- **Release candidates:** tag `vX.Y.Z-rc.N` as a GitHub pre-release on `next`, with `version` in `pyproject.toml` set to `X.Y.ZrcN` (then `uv lock`) in the commit it tags. Only a staging server set to Release candidates on its Updates page (Update from) installs them; one set to the `next` branch installs that branch's latest commit. `update-from-app.sh` refuses both unless root's `/etc/club-minutes/env` has `CLUB_MINUTES_STAGE=`. The Release workflow runs on main only, so it never tags an rc.
- **Updating from the app:** admins in admin mode see "Version X is available" and an **Updates** page with **Update now**. It writes `update-request.json` in the data folder; the root-owned `club-minutes-update.path` unit sees it and runs `deploy/update-from-app.sh` (which runs `update.sh` and records the result). `update.sh` installs and enables that unit, so the first update after this feature arrives is still by hand. **Back up first** is ticked by default once backups are set up: a full backup (kept and sent off as usual) runs before the update is requested, and if it fails the update doesn't start.
- **Installs the release, and rolls back:** "Update now" and the nightly auto-update ask for a release by its version; `update-from-app.sh` accepts only a plain `X.Y.Z` from the request file (the app writes it) and runs `TAG=vX.Y.Z update.sh`, which installs that tag, not the latest main. If the sign-in page doesn't answer within 5 minutes after the restart (startup takes about a second), `update.sh` resets to the commit it had, reinstalls and restarts, and exits non-zero (the Updates page shows it failed). Run by hand without `TAG`, `update.sh` still installs the latest main.
- **Automatic updates** (Updates page → Turn on; off by default, needs backups set up): `club-minutes-autoupdate.timer` runs `club-minutes auto-update` hourly at :30, and it acts only at the hour set on the Updates page (2:30 by default). If no release newer than the running one has deploy notes (all of them are read, not only the newest), it takes a full backup (none, no update), asks for that release as above, waits for the outcome and emails the admins. A release with deploy notes is only emailed about (once); one that failed isn't tried again until an admin acts.
- **Changing how data is stored** (a file renamed, a field reshaped): add a step to `STEPS` in `src/club_minutes/upgrade.py` with a test that runs it on data of the old shape, so a 1.x needs no deploy notes. The app runs any steps the data folder hasn't had (`data-version` says which it has) at start, after a copy to `before-upgrade/`; if the new version doesn't start, `update.sh` puts that copy back (`club-minutes data-undo`) before going back. Never change or remove a released step, and make each safe to run twice (it can be stopped part way). An older version refuses data newer than it knows.
- Every pull request runs the tests (the Tests workflow).

## Writing the changelog
It follows [Keep a Changelog](https://keepachangelog.com): each version's lines go under `### Added`, `### Changed`, `### Fixed`, `### Security` and `### Removed`, in that order (only those with something in them), then `### For server admins`. Members read the Unreleased section on the About page as What's new, so it's written for them, not for developers. About leaves out each release's `### Security` and `### For server admins` (a release with nothing else isn't listed there); admins see the whole section on Admin → Updates.
- **What changed, not how to use it:** one short line per change, in plain words: what members can do now, or what works differently. No how-to, no where to set it up or how to turn it off, no list of options: that's the guides' job.
- **No line for a fix to something new in this release:** members never saw the bug, so it's part of that feature's line. Development-only work (tests, checks, tooling) gets none either (the `no-changelog` label if the check asks).
- **Biggest first** in each group. **Changed** holds only the few changes members will notice most; the rest needs no line.
- **A security fix:** one short line, no how-to ("fixes a way a roster keeper could gain another member's access; update soon"); the details go in a GitHub security advisory published once the release is out.
- **For server admins:** a line at most, on what they must know before updating (a data upgrade, a change of owner), pointing to the server admin guide for the details. Steps the update needs by hand are Deploy notes (above), which the Updates page shows.
- **Before a release, reread the whole section** as a member would: merge lines about the same feature, drop what later changes overtook, and check every sentence still reads.

## Compatibility (what a 1.x keeps)
From 1.0.0 on, a club updates within 1.x without doing anything by hand, so a 1.x may add but never take away or rename. Breaking any of this waits for 2.0 (the first number in the version: see CHANGELOG.md).

What a club relies on:
- **club.yaml:** every setting's name and meaning, and the values it takes.
- **The data folder:** what's stored in it, which a newer version may reshape only through an upgrade step (Changes and releases, above); and the backup format, so an older backup can always be restored.
- **The server:** the folders (`/opt/club-minutes`, `/var/lib/club-minutes`, `/etc/club-minutes`), the service and timer names, the `club-minutes` commands and their options, the `CLUB_MINUTES_*` environment settings, and `setup.sh` and `update.sh`.
- **Addresses others keep:** members' calendar subscription links (`/calendar/feed/…`, `/calendar/public.ics`) and public calendar page, sign-in links in emails already sent, and any page address in an email or a bookmark (a moved page answers its old address with a redirect, as Backups' does).
- **The roster API** (`/api/roster`, for a club's own tools, such as a chat bot): its token, its fields and what they mean. Fields may be added; none removed or renamed.

The rules:
- **A new setting has a default** that keeps things as they were, so a club.yaml from 1.0.0 still starts. A setting that must be given is a 2.0 change.
- **An old name keeps working until 2.0.** To rename a club.yaml setting, add it to `RENAMED` in `src/club_minutes/club.py`: the app reads the old name as the new one and says so on the Admin page. A setting saved on Admin → Site (site-settings.json) is renamed with an upgrade step instead, since the app wrote it. A renamed command, service or address keeps its old name alongside (an alias, a second unit, a redirect).
- **A name is never reused** for something different, even after the old thing is gone: pick a new one.
- **Removing a feature is a 2.0 change.** Switching a module off (like chow) is the club's choice, and switching it back on finds its data where it was.
- When in doubt, a release needs Deploy notes only for something a club chooses to do, never for something it has to.
- **Repo checks** (`tests/test_guards.py`, in every PR's tests): the screenshots are up to date (for a release, above) and each is used; links and pictures in the README and guides lead to files that exist, and every app address they name in backticks (`/calendar/public.ics`) is a page; and no tracked file has a real-looking callsign (only four-letter suffixes, KO4CGQ, and W8LBZ as the old name), email (only example.org/.com/.net and other reserved names) or phone number (only 555-0100 to 555-0199).
- **The guards:** `tests/test_compat.py` (in every PR's tests) fails if a 1.0.0 club.yaml with every setting no longer starts (`tests/fixtures/club-1.0.0.yaml`: never edit it), a setting the code reads isn't in `club.example.yaml`, a 1.0.0 setting is no longer read or renamed, or a command, address, roster API field, systemd unit or `CLUB_MINUTES_*` setting from 1.0.0 is gone. Don't edit its lists to make it pass: keep the old name working. Adding is always fine.

## Security checks
Run on every pull request, every push to main and **every Monday**, so a newly published advisory turns up even in a quiet week. Any of them can also be run by hand: Actions → the workflow → Run workflow.
- **Security workflow:** `pip-audit` checks the locked Python packages (`uv.lock`) against the PyPI and OSV advisory databases; `gitleaks` looks for keys, tokens and passwords anywhere in the git history.
- **CodeQL workflow:** GitHub's code scanner for the Python and JavaScript (injection, script injection (XSS), unsafe redirects...). Findings are under Security → Code scanning.
- **Dependabot** (`.github/dependabot.yml`): a weekly PR for newer Python packages and GitHub Actions once a version has been out 7 days, and one right away for a security fix. `.github/workflows/dependabot.yml` asks `dev/dependabot.py` what happens to each (with the repository's GitHub App, so the required checks run on what it does):
  - **Merges itself** once the required checks pass: only `uv.lock` (or pinned Actions from `actions/`, `github/` or `astral-sh/`) changes, every update is a patch or minor one, and the app's own packages are unchanged (development tools only).
  - **Releases itself:** a high or critical security fix (CVSS 7.0 or more) in an app package, once the fixed version has been on PyPI 48 hours (a poisoned "fix" from a hijacked maintainer is usually pulled by then; until then the PR is labelled `security-hold`, the maintainer is told once (a comment, and a review request to the `SECURITY_CONTACT` repository variable) and it's looked at again every 6 hours; a **`release-now`** label releases it at once, for a confirmed serious issue), while main holds nothing unreleased (main is always releasable): the same PR gets the patch version and its CHANGELOG section, and the Release workflow tags it once it merges. A server with automatic updates on installs it that night.
  - **Waits for review:** everything else: a major version, another publisher's Action, a security fix below high. An ordinary app-package update waits for the next release.
- **Lint:** with the tests (`tests/test_lint.py`), here and on GitHub, each at the version pinned in `uv.lock`: ruff on the Python (its default rules), shellcheck on `deploy/*.sh` (several run as root), zizmor on the GitHub workflows. GitHub's Tests also run the newest ruff as a warning (the ruff-latest job: red there doesn't fail the check), and Dependabot opens a "lint" pull request of its own when any of the three has a new version: fix what it flags in that PR, then merge it to move the pins. gitleaks (Security workflow) is a pinned download Dependabot can't update: its gitleaks-latest job warns when a newer one is out (set `GITLEAKS_VERSION` and `GITLEAKS_SHA256` in security.yml).
- **Tests:** `tests/test_security.py` tries every route signed out (only the public pages answer), officer and admin pages as a member, and members changing what isn't theirs; a new route is covered automatically. The mobile test opens every page in real browsers (Chromium, Firefox and WebKit, Safari's engine), again in dark mode (failing on text under 3:1 contrast with its background), and fails if the Content Security Policy blocks anything or a script errors. The policy runs scripts only from the app's own files or the `<script>` blocks a page was given a one-time nonce for: no inline `on…=` handlers (use `data-confirm`, `data-autosubmit`, `data-select`, `data-tick` from `base.html`, or a listener in a `<script nonce="{{ csp_nonce }}">`).
- **Changes only from the app's own pages:** a POST (or PUT, PATCH, DELETE) that a browser marks as from another site or a sibling host (`Sec-Fetch-Site`), or whose `Origin` isn't the address it was sent to, gets a 403 (`same_origin_only` in `web.py`). The sign-in cookie's `SameSite=lax` stops other sites but not sibling hosts on the same domain (other names on the tailnet). New forms and `fetch` calls on the app's own pages need nothing.
- Actions in the workflows are pinned to a commit, with the version in a comment; Dependabot updates both.
- **Repository settings** worth having on (Settings → Code security): Dependabot alerts, secret scanning and push protection (blocks a push that contains a key).

## Checks before a push
`dev/checks.sh` runs here what GitHub runs on a pull request, so nothing turns up only there: the tests (with ruff, shellcheck, zizmor and the browser tests), pip-audit on the locked packages, gitleaks at the version `security.yml` pins on every branch and tag (GitHub's scan reads them all, not only main), and CodeQL with the `security-extended` queries on the committed files (Python and JavaScript). It also runs the **upgrade check** (`dev/upgrade-check.sh`: the last 1.x release builds the demo club's data, then this code starts on it, so upgrade steps meet data of the real old shape) and the **changelog check** (`dev/changelog-check.sh`: a change to `src/` or `deploy/` needs a line under Unreleased in CHANGELOG.md; on GitHub the `no-changelog` label skips it). What goes in it: Writing the changelog, above. About four minutes for everything; `--quick` skips the tests when they've just passed.

**What runs depends on what changed** since `CHECKS_BASE` (default `origin/main`; on a stacked branch, set it to the branch below), sorted by `dev/changes.sh`: a change of only docs, screenshots or Markdown runs just the quick checks (pip-audit, gitleaks, the changelog and `pytest -m docs`); anything else runs everything. The slow checks (all the tests, the upgrade check, CodeQL) run anyway when their last pass here is older than `CHECKS_MAX_AGE_DAYS` (7), noted in the cache folder; `--full` always runs everything (before a push). GitHub does the same: a docs-only pull request reports its browser tests and CodeQL as "skipped (docs only)", which counts as a pass, so the required checks never wait; pushes to main, and the Monday run, do everything. Tools live in `~/.cache/club-minutes-checks`: gitleaks downloads itself (checked against the pinned checksum); for CodeQL, unpack `codeql-bundle-linux64` from github/codeql-action's releases there (checking its `.checksum.txt`), or set `CODEQL`.

CodeQL findings reviewed as false positives are listed in `dev/codeql-accepted.txt` (rule, file, the line's text, why), matched by the line's text so moving code doesn't bring them back. A new finding fails: fix it, or, after a careful look, add it there with the reason and dismiss it on GitHub with the same words. To run the checks on every push, add a `.git/hooks/pre-push` that runs `dev/checks.sh`.

## Roles and permissions
What a member may do is a **permission** (`PERMISSIONS` in `src/club_minutes/club.py`: lead, correct, calendar, chow, contacts, emails, status, oversee (Roster changes), moderate (business items, comments, pictures, the calendar log), treasurer, money, members, roster_emails), and **roles** say which permissions each gives. A new check asks `archive.club.may(member, "permission")`, plus `admin_mode(request)` (admins in admin mode may do everything); never `member.officer`, `member.role` or words in a title. `Club.role_table()` is every role: the built-ins (`ROLES`, with what they allow as they ship) and the club's own, each given by whole office titles (`Club.office_list()`; any capitals; a title that isn't an office gives nothing) and by members picked by hand. Admins edit it on Admin → Site → Roles; `data/roles.json` keeps each role's picked members under its key (1.0's shape, so a rollback still reads Meeting leader and Calendar editor) and, under `table`, each role that differs from how it ships. Two built-in keys are older than their names: `board` is Minutes editor and `minutes_editor` is Meeting leader. A save is refused if any permission would be left with no role; `money` always brings `treasurer`. Admin isn't a role: it's `admins:` and Admin → Security, with admin mode and its re-confirm. A new permission goes in `PERMISSIONS` (and in a built-in role's defaults if one should have it) and shows on Site → Roles by itself.

## Writing a plugin (experimental)
A plugin is a Python package an admin installs next to the app and ticks on at Admin → Site → Features. Experimental: the API (`PLUGIN_API = 1` in `src/club_minutes/plugins.py`) may change; a plugin written for another number is skipped and Site says so.

**Releasing it.** Servers install a plugin from its Git repository with `deploy/plugin.sh` (server admin guide → Plugins), at its newest `vX.Y.Z` tag, and move it to its newest tag at every app update. So tag a release only when it works with the app's current plugin API; when the API number goes up, tag one built for the new number soon after the app's release (until then, servers turn the plugin off, or wait for it before updating, as each admin chose).

**Finding it.** An entry point in the group `club_minutes.plugins`, named the same as the module's `NAME`:
```toml
[project.entry-points."club_minutes.plugins"]
hello = "hello_plugin"
```
The module declares `API = 1`, `NAME` (lowercase letters and digits; also its address prefix, `/` and the name; refused if the app has that address already), `TITLE`, `DESCRIPTION` and, optionally, `NEEDS = {"email"}` (Site then says it needs members' email addresses). Everything below is optional. A plugin that raises when it loads, or has another API, is skipped and logged and the app runs on; if an admin had turned it on, the admins get one email per start.

**What it may add.**
- `router`: a FastAPI `APIRouter`, mounted at `/<NAME>`. **The app enforces access, not the plugin:** every path needs sign-in unless it is in `PUBLIC` (a set of paths on the router, route paths like `{"/open", "/door/{room}"}`; a `{part}` stands for any one part of the address, never a `/`; open to every method, not just GET); anything under `/<NAME>/admin` needs an admin in admin mode (others get "not found"). While the plugin is off every one of its addresses is a 404. Write the page's own checks (`api.may`) for permissions.
- `PERMISSIONS`: `{"edit": "edit the board"}`. They show on Site → Roles, as `hello.edit`, while the plugin is on; no role has them until an admin gives one. Ask with `api.may(member_id, "edit")`; admins in admin mode count too: `api.may(...) or api.admin_mode(request)`.
- `NAV`: `[("Hello", "/", None), ("Editor", "/edit", "edit")]`: label, path on the router, and the permission needed (or `None`); shown in the menu to the members allowed (admins in admin mode see all).
- A `templates/` folder next to the module. Its files are `"<NAME>/file.html"`; they extend `base.html`. Render with `api.page(request, "file.html", **context)`, which gives the app's menu and styles. The same rules as the app's templates: no inline `on…=` handlers, a `<script>` needs `nonce="{{ csp_nonce }}"`, never `|safe` on text members typed.
- `GUIDE`: the path of a Markdown file (relative to the module), shown under Help while the plugin is on.
- `nav_ready(api)`: `False` hides the plugin's menu links (say, until its settings are filled in); admins in admin mode still see them, to finish setting it up. An error in it counts as `False`.
- `calendar_links(api)`: a list of `(label, url)` buttons on the calendar event form that fill in the online link. A `url` that starts with `/` (a page of the plugin) gets the app's own address put in front.
- `form_action(api)`: a list of origins (`["https://meet.example.org"]`, each `https://host` or `https://host:port`; anything else is dropped) that the pages' forms may end on, for a form that redirects to another site. The app adds them to the Content Security Policy's `form-action` **only** on the plugin's own addresses (`/<NAME>` and below) while it's on, never elsewhere.
- A settings page at `/<NAME>/admin`: while the plugin is on it's a tab of Admin → Site, after the app's own (its TITLE), and Site → Features links to it too. Start the page with `{% include "_site_head.html" %}` (the Site heading and tabs, this one marked), as the app's own Site tabs do. The app writes every change there (any method but GET) to the admin log itself. Before a sensitive one (a new secret, say), ask for a fresh confirmation: `if again := api.fresh(request, "/<NAME>/admin"): return again` sends the admin to confirm with a passkey or emailed link, then back to that address, unless they did in the last few minutes.

**What it gets.** The app sets `api` on the module before the first request (read it inside handlers, not when the module is imported):
- `api.member(id)`: `{"id", "name", "active"}` or `None`; nothing else about a member.
- `api.may(id, perm)`, `api.who(request)` (the signed-in member's id, or `None`), `api.admin_mode(request)`.
- `api.roles(id)`: the role keys the member holds; `api.role_labels()`: `{role key: its name}`, for a settings page that picks roles.
- `api.base_url(request)`: the address members reach the app at (`https://host`), for links a page shows.
- `api.email(id)`: only with `NEEDS = {"email"}`; otherwise it raises `PermissionError`.
- `api.storage.load()` / `.save(dict)` / `.update(change)`: one JSON file for the plugin in the data folder (`plugins/<NAME>.json`, in the backups), each call locked and saved atomically. To change what's stored, use `update(lambda d: ...)`: a `load()` then `save()` isn't one locked step, so two requests could lose each other's change.
No `Club`, no sign-in internals, no other plugin's storage. `tests/test_plugins.py` and `tests/fixtures/helloplugin/` are a small working example.

## Election days for another state
Election days are worked out from a state's rules in a small file in `src/club_minutes/regions/`, named for its code: `us_oh.py` is `us-oh`. A file there is listed on Admin → Site → Features by itself; nothing else needs changing. It has:
- `NAME`: how the list shows it, e.g. `"Ohio: primaries and general election"`.
- `elections(lo, hi)`: every election day from `lo` to `hi` (dates) as `[(date, name, notes)]`; `notes` is shown with the event (polling hours, where to find your ballot).
- A docstring citing the law the rules come from, and a `shortcut:` line with the year they were checked.

Copy `us_oh.py` and change its rules; `nth_weekday(year, month, weekday, n)` (Monday 0, n -1 for the last) is there for "the first Tuesday after the first Monday" kinds of rules. Add a test like `test_holidays_and_elections_are_none_unless_club_yaml_picks_a_region`. Holidays need no file: they come from python-holidays, and a club adds its own on the Features tab.

## Links page icons
Besides the 21 built-in icons, the icon picker searches about 3,400 brand logos from [Simple Icons](https://simpleicons.org) (CC0). They're stored in the repo (`src/club_minutes/simple_icons.json`), never loaded from a CDN, and drawn in the club's color like the built-in icons. To update them: `python3 deploy/update-simple-icons.py [VERSION]`.

## Callsign changes
A member's id is stored in the roster's `id` column (`roster.to_members` reads it; a row without one gets the old lowercase callsign or name slug) and never changes. Members from before ids were stored keep the id they had (data version 5 filled the column); a new member gets `m` and six random letters or digits (`membership.new_id`, never one that reads as a callsign). So **New callsign** changes nothing but the roster (`callsign.change`): the callsign, the old one added to the member's `aliases`, a Membership Log row. No backup or passphrase, no file renamed. `Club.canonical` maps an old or current callsign that isn't the id to the member (club.yaml's `admins:` and `email.only_to` included); `Club.resolve` does the same for a `/members/…` address, which takes a callsign (current or former) or an id, and `Club.member_url` writes the address: the lowercase callsign, else the id. Build every link to a member's page with it.

`rename_id` (`club-minutes rename-id OLD NEW`) is kept to finish a rename that stopped partway under the old scheme: it renames an id in current state (`chow.json`, `business.json`, `events.json`, `calendar-feeds.json`, `ask-about.json`, `email-prefs.json`, `settings.json`, `treasurer.json`, `admins.json`, drafts' `console.json`), the minutes' front matter and report tags (never their text), the sign-in database and the picture. Logs (`*.jsonl`) keep the old id as history.
