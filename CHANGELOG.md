# Changelog

What changed in each version of Club Minutes. Ideas and requests: the repository's [Issues](https://github.com/KO4CGQ/minutes/issues).

Versions follow [semantic versioning](https://semver.org): the first number goes up for a change to settings, folders or command names that a club has to act on (a 2.0), the middle for new features, the last for fixes. Each version is a git tag (`v1.0.0`), and the app's footer shows the version that's running.

## Unreleased
- **Security** (from a security review of the work above): a new callsign keeps an admin's suspension and an open recovery (they held the old id, which lifted the suspension); a recovery whose nominee is no longer active ends without suspending anyone, instead of leaving the club with no admin; two officers approving at once can't lose one approval, and the daily job and the page can't both complete it; a new email is checked again when its link is opened (the address still free, and whoever asked still allowed to); the Jitsi secret must be at least 32 characters.
- **Fixed:** on Site → Roles at phone size, the permission checkboxes shrank beside labels that wrap.
- **Data:** 1.1.0's data is data version 3. The update keeps the copy from before it, a failed update puts that back, and 1.0 refuses 1.1's data rather than misread it (it would have dropped custom roles, ignored suspended admins and failed sign-in links). Minutes files are written whole or not at all; a correction that fails to save leaves the minutes as they were; a new callsign keeps a member's right to correct the minutes they led or recorded.
- **Video meetings (Jitsi, optional):** with `modules: {jitsi: true}`, a `jitsi:` block and `CLUB_MINUTES_JITSI_SECRET`, **Video meeting** in the menu (`/meet`, `/meet/<room>`) takes signed-in members to the club's own Jitsi Meet server with a 5-minute token saying who they are and whether they host. A new permission, "host video meetings" (Officer and Meeting leader as they ship), shows on Site → Roles while it's on. Off, nothing about it shows. Server admin guide → Video meetings has what the Jitsi server needs.
- **Removed:** support from before 1.0.0: backups made by 0.x (under the app's earlier name) no longer restore here (it says so; a 0.x install restores them), and sign-ins from 0.x (the old session cookie, long expired) no longer count.
- Development only: the developers guide (Checks before a push) covers the upgrade and changelog checks, docs-only runs, `CHECKS_BASE` and `--full`.
- **Recover admin access:** if the club can't reach its admins, or one works against it, the officers can make a member an admin and suspend admins from the app (`/recover`, linked from the Offices page). A majority of the officers (at least 2) approve, each confirming it's them; the member accepts; then 7 days. An admin's objection makes it two-thirds and 14 days, so it can delay but not stop it. Every member is emailed at each step; a suspended admin's rights (club.yaml's too) stop counting until another admin lifts it.
- **Security:** there's always an active admin: the last one can't be set Inactive or Silent Key, or removed (an Inactive admin can't sign in, so doesn't count), and the Admin page warns "You're the only active admin" until there's another. A roster keeper could set the only admin Inactive and lock the club out of its admin tools.
- **Security:** changing another member's email or status is its own permission (Roster keeper has both as it ships), and nobody changes the email or status of a member who can do more than they can (an admin, or someone with a permission they lack); an admin in admin mode may. A roster keeper could change a member's email, ask for a sign-in link to it and be signed in as them: now a new email waits for a link sent to the new address, the old address is told at once, and the change signs the member out everywhere (their own change too). The confirmation page has a button, so a mail scanner opening the link changes nothing.
- **Fixed:** a member changing their own email never got the new one: the confirmation link opened the Email settings page instead (it's `/email/confirm` now).
- **Custom roles and permissions:** on Admin → Site → Roles an admin sets what each role allows, which offices give it and which members are picked for it, and adds, renames and removes the club's own roles; each built-in role has **Back to the built-in**. **Minutes editor** splits in two: **Meeting leader** runs the console (the members picked as Minutes editors in 1.0 keep it), and **Minutes editor** corrects published minutes (holders of any office, as Board was). A new **Secretary** role gets the roster emails (new members, roster changes, the chow list). Seeing and undoing Roster changes and moderating (any business item, motions and suggestions, comments, pictures, the calendar change log) are now two permissions; officers have both. A save that leaves a permission with no role is refused, recording money always brings the Treasurer pages, and no role gives admin. Site → Roles' offices table loses its "Adds members" column: that's the Roster keeper role's offices now. New offices are added with **+ Add an office** (one empty row without JavaScript) instead of two empty rows.
- **Security:** roles come from whole office titles only (any capitals). A title that merely contains an office's name ("Assistant Treasurer", "Secretary emeritus") gave the Treasurer's money rights, added members, or got the Secretary's and the arrears emails; titles that aren't offices now give no role, so the titles a roster keeper types can't hand one out. The roster API's `officer` field means "has the Officer role".
- **Correct these minutes:** minutes already in the archive are corrected on their page by the meeting's leader or recorder, any board member, or an admin in admin mode, with a line saying why; guests and items are added with + Add, and a preview shows the changes side by side before saving, with the words that changed marked. The old version is kept (`minutes.v1.md` beside `minutes.md`) and linked from the new one's footer, which shows who corrected it, when and why; the PDF is named `-v2`. Members get a "corrected minutes" email listing what changed, the same way they get the minutes, unless the box is unticked (the footer then says "no notice sent"). Imported minutes get **Mark as reviewed**; a correction reviews them too. A new permission, "correct", goes with the Minutes editor role (holders of any office). For imported minutes whose corrected text came later, `club-minutes import-correction DATE corrected.pdf --by CALL --reason "…" [--on DATE]` puts the original PDF's text back as version 1 and makes the corrected PDF version 2, with no notice.
- **Security:** the meeting console only works on minutes still in progress. Starting a meeting on a date whose minutes are already in the archive, or opening, saving, submitting or discarding them, is refused with a pointer to Correct these minutes: a second Submit rebuilt Old Business and Upcoming Chow from that day's state and emailed the club again, and imported minutes could be reopened.
- **Security:** Admin → Security → Failed attempts also lists hostile requests: scanner probes (asking for `.env`, `wp-login.php` or other `.php` files), which get "Not Found" and count toward a ban; and, never counted, requests sent from another site's page, actions a member's role doesn't allow, and uploads over the size limit. Each shows the address, device and what was tried.
- **Security:** the console's save checks what it's sent: a request of the wrong shape gets "That request wasn't readable" (it was a server error), a save over 256 KB is refused (a long meeting is a few KB), and member attendance keeps only roster ids (any status, an old callsign becoming the current one); guests are unchanged. A picture claiming billions of pixels, as a profile photo or the logo, gets "That picture is too big" (it was a server error).
- **Security:** the automatic ban stops only signing in: members already signed in from a banned address keep working, and the public calendar stays open (a clubhouse or a phone carrier puts many people behind one address). Clicking an old or used sign-in link no longer counts toward a ban, only a link the app never sent. IPv6 bans cover the address's /64 block, which the Security page shows; bans made by 1.0 still hold.
- **Security:** sign-in link limits count per address, so someone asking again and again for a member's link no longer uses up the member's own: 5 an hour for a member from each address, 15 an hour from all addresses together. Asking again within two minutes sends nothing more and no longer counts toward an automatic ban (a click while the email is still on its way).
- **Security:** "Email me a link" answers before the email goes out, so a member's address and anyone else's answer in the same time (a member's took about a second longer, which showed who's a member).
- **Security:** turning on admin mode with a passkey needs it to check your PIN, fingerprint or face; a security key that's only tapped was accepted. Signing in still takes a tap, so older keys keep working; an emailed link still turns admin mode on too.
- **Security:** the Email log, and the server's log when no SMTP is set up, show sign-in, new-email and admin-mode links with their one-time code hidden (`t=[hidden]`), so an admin reading the log can't open a member's link and be signed in as them. The emails themselves are unchanged.
- **Security:** every admin address answers a member who isn't an admin with "Not Found", the same as an address that doesn't exist (the admin-mode, update and view-as pages said "You aren't listed as an admin", and four Security-page actions answered "missing field" before checking who was asking). Admins with admin mode off still get the confirmation page.

## 1.0.1 (2026-11-15)
- **Security:** a roster keeper could type an admin's callsign into their own "Other spellings" and become that admin (the admin losing admin rights, and their sign-ins becoming the keeper's); the same worked for any member's roles and items. Another member's callsign is now refused there, and a roster that has one anyway (or a former callsign two members both list) ignores it.
- Development only: smarter checks. A docs-only change (Markdown and `docs/`, `dev/changes.sh`) runs just the quick checks (pip-audit, gitleaks, the changelog, `pytest -m docs`), locally and on pull requests; the slow ones (every test, the upgrade check, CodeQL) run for anything else, on every push to main and every Monday, and locally whenever they last passed over a week ago (`dev/checks.sh --full` runs everything).
- Development only: a pull request that changes the app (`src/`, `deploy/`) needs a CHANGELOG line, or the `no-changelog` label (`dev/changelog-check.sh`, also in `dev/checks.sh`); shellcheck covers `dev/*.sh`.
- Development only: an upgrade check on every pull request (`dev/upgrade-check.sh`, also in `dev/checks.sh`): the last 1.x release builds the demo club's data, then the new code opens it and checks that every member and every meeting's minutes are still there, as an admin and as a member.
- Development only: the secret scan no longer allows the icons file's pre-1.0 path (the 0.x tags it lived in are deleted), and `dev/checks.sh` scans branches and tags only, as GitHub does (not local worktrees).

## 1.0.0 (2026-11-13)
**Initial release.** Club Minutes has been redesigned so any amateur radio club can set it up and shape it to its own needs (its agenda, offices, dues, calendars and look) from the app. Earlier test versions (0.x) aren't listed here. From 1.0.0 on, settings, folders, services and command names stay the same from one version to the next; a change a club would have to act on waits for 2.0 (the developer guide's Compatibility section lists what that covers).

- **Meeting night:** the leader console takes the minutes live, step by step through the club's agenda (its own sections, order and hints), with attendance in person and online, guests, reports, Old and New Business, motions (mover, seconder, result) and upcoming events from the calendar. Members follow along live. One console holds the meeting at a time (others see it read-only, with Take over). Submit publishes the minutes and emails them to every member.
- **The minutes:** every meeting as a page and a PDF with the club's logo and colours, attendance stats, per-member history and guest tracking; one search box for minutes, members (nicknames too, and members' other spellings), guests, business, chow nights and events. Older minutes can be imported from PDFs with a plain parser (no AI), marked "imported, unreviewed".
- **Home:** what's next for each member: the next meeting (with Join online), their chow night and swap requests, their business items and dues, the latest minutes and what's coming up.
- **Business items:** Old and New Business carried from week to week, with owners, due dates, reminders, comments and history, and notes for the next meeting.
- **Calendar:** the club's events, planning and community calendars kept by the app, with chow nights, shared birthdays, business due dates and holidays for any country, state or region (plus the club's own); a place and an online meeting link per event; .ics import, private subscription links for phones and calendar apps, and calendars the club chooses to make public. The weekly meeting is set from Site → Club, from a Starting date on.
- **Members:** sign-in with a passkey or an emailed one-time link (no passwords); the roster kept in the app, with profiles, pictures, offices and their holders over time, and who changed what; each member chooses which emails they get, including a meeting-day email.
- **Chow** (an optional module): the rotation, swaps between members, reminders before your night, and who provided, missed or covered each night.
- **Treasurer:** who owes what (dues, fees, an optional certificate each member buys once), payments and expenses, regular bills and bills read at meetings, and committee funds; each member sees their own figures on Home.
- **Site** (admins): the club's name, callsign, logo, colours (light and dark), meeting night, place and online link, agenda, the club's offices and roles (what each allows and who has it), optional features, holidays and election days, bylaws references, date formats and names never recorded, set in the app over the server's club.yaml.
- **Admin and security:** admin mode for an hour at a time, confirmed with a passkey or an emailed link; admins managed in the app; viewing the app as another member (read-only); the guides in the app, with pictures and in the search (Help for members and officers, the server admin guide under Admin); a Security page with sign-ins, devices (sign one out), failed attempts with details, and bans (automatic after repeated failures from an internet address); changes accepted only from the app's own pages; a strict Content Security Policy.
- **Running a server:** one script installs it on Debian (`setup.sh`), with a hardening guide (fail2ban, keys-only SSH, automatic updates, the app's port closed to the LAN), and `club-minutes first-member` starts an empty roster; updates from the app (Update now, or nightly), rolled back if the new version doesn't start; a new version that stores data differently reshapes it by itself (after a copy, put back if it doesn't start), so updates within 1.x need no steps by hand; encrypted backups on a schedule, kept on the server and optionally sent to Backblaze B2 or Google Drive; an optional staging server with a one-way copy of the live data, whose email goes only to whoever's testing.
- **Every page works on a phone,** in light and dark mode. Every change is checked by the tests in Chromium, Firefox and WebKit (phone width, dark-mode contrast, the security policy), lint (ruff, shellcheck, zizmor), guards that what a club relies on is still there, that the screenshots match their pages and the docs' links work, and that no real-looking contact details get in, CodeQL, pip-audit and gitleaks. Vulnerabilities can be reported privately (SECURITY.md).
- **Deploy notes:** a server installed before 1.0.0 moves to the new names once, by hand, with the maintainer's move script (Update now can't do it, and this note keeps the nightly update from trying). A new install needs nothing more: `setup.sh`, then the server admin guide's Getting started.
